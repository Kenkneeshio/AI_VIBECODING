# Integration choices

| Path | Tuya cloud at runtime? | Separate phone for this migration? | Fit for this home |
| --- | --- | --- | --- |
| [Official HA Tuya integration](https://www.home-assistant.io/integrations/tuya/) | Yes; its HA IoT class is Cloud Push | Existing account/app pairing remains part of the ecosystem | Current fallback; does not meet local-control goal |
| [make-all/tuya-local](https://github.com/make-all/tuya-local) with manual details | No for supported LAN devices | No when valid existing key and ID are available | **Pilot choice:** broad device profiles, direct HA entities, no extra service |
| [rospogrigio/LocalTuya](https://github.com/rospogrigio/localtuya) with manual details | Optional cloud API; not required for local operation | No when valid existing key and ID are available | Version 5.2.3 is installed but unused; its documented protocol range is 3.1–3.4, so it is **not** the current fallback for the five LAN-discovered 3.5 devices |
| New standalone HA add-on/gateway | Depends on implementation | Possible | Adds protocol and entity maintenance burden; only justify after an upstream gap is proven |
| Convert compatible existing Tuya hardware using [Tuya CloudCutter](https://github.com/tuya-cloudcutter/tuya-cloudcutter) and [OpenBeken](https://github.com/openshwprojects/OpenBK7231T_App) or [ESPHome](https://esphome.io/components/libretiny/) | No Tuya cloud after successful conversion | Model- and method-specific; some setup paths may need an app or flashing hardware | Preserves hardware, but depends on the exact chipset, firmware, and exploit profile; experimental and potentially disruptive, so assess separately from the LAN pilot |
| Replace a device with native Zigbee, Matter, or ESPHome hardware | No Tuya cloud when locally commissioned | Depends on device and commissioning method | Hardware replacement for unsupported or unreliable models; assess range, radio/hub needs, and HA support before purchase |

The upstream integrations differ despite similar names. `tuya-local` is `make-all/tuya-local`; `LocalTuya` is `rospogrigio/localtuya`. Do not enable both to connect to the same device at once. `tuya-local` states many Tuya devices permit only one local connection; [LocalTuya](https://github.com/rospogrigio/localtuya) likewise needs the device key and ID for manual operation.

For architecture, use Green's wired Ethernet and local Wi-Fi reachability for eligible Wi-Fi devices. No new USB radio is required for that path. Zigbee devices should be assessed separately for direct [ZHA](https://www.home-assistant.io/integrations/zha/) pairing with a [Connect ZBT-2](https://www.home-assistant.io/connect/zbt-2/) set to Zigbee. The ZBT-2 cannot run Zigbee and Thread simultaneously. Maintain a cloud-only holdout list for devices without a verified local path.

Firmware conversion is distinct from replacing hardware. CloudCutter supports only certain unpatched chips/firmware and warns that its process is experimental and disconnects the device from Tuya's app and servers. OpenBeken can expose local MQTT/HA entities, while ESPHome's LibreTiny support covers selected chipsets; each requires a correct device-specific configuration. A Tuya LAN protocol version such as 3.5 does **not** establish CloudCutter compatibility. Do not flash a device as part of the one-device LAN pilot. [CloudCutter support and warnings](https://github.com/tuya-cloudcutter/tuya-cloudcutter#supported-devices), [OpenBeken features](https://github.com/openshwprojects/OpenBK7231T_App#features), [ESPHome LibreTiny support](https://esphome.io/components/libretiny/).

### What the audit does and does not show

The existing private Xtend cache held 42 keys: 36 direct devices and six gateway subdevices. Thirty-nine advertise `support_local` (36 direct, three subdevices). By category, the 42 records are 18 bulbs, five on/off switches, two dimmers, two plugs, two air monitors, and 13 other devices or gateways. Only five direct devices advertised themselves on the LAN in this audit: one bulb, one wall switch, one track-light switch, and two air monitors. All five advertise protocol 3.5. Three read-only **raw LAN DPS status** probes returned in 0.297–0.406 seconds. These are not HA UI latency measurements. The counts establish a worthwhile pilot, not a purchase or migration count; 42 keys do not mean 42 reachable devices. They do not prove control datapoints, internet-offline operation, restart resilience, or compatibility for every model. Gateway subdevices need separate assessment even where their local-capability flag is true.

### New devices and privacy

Manual local configuration is possible only when the device ID, current local key, and host are known. `tuya-local` says a key changes after re-pairing. Some battery and hub-connected devices are not directly supported. Using a LAN integration does not stop a Tuya device from sending data to its cloud; isolate outbound traffic only after testing each device and preserving a recovery path. These limitations come from the [upstream README](https://github.com/make-all/tuya-local).
